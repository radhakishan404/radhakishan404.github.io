Claude Code · Agents · gstack

Garry Tan's gstack is not a prompt pack. It is an AI software team.

The President and CEO of Y Combinator open-sourced the way he runs Claude Code. The interesting part is not that it has many prompts. The interesting part is that it turns vague solo-builder work into a structured company-like workflow: CEO review, engineering review, design review, code review, QA, security, documentation, release, and retro.

Why people are paying attention

Garry Tan is not a random developer posting a prompt list. He is President and CEO of Y Combinator, the accelerator behind companies like Airbnb, Stripe, Dropbox, Coinbase, DoorDash, Reddit, and Instacart. YC's own profile says Tan is also a designer, engineer, former early Palantir designer/engineering manager, Posterous founder, and former YC partner who built parts of YC's internal founder experience.

That context matters because gstack is built around a startup operating model. It does not ask Claude Code to be one generic assistant. It asks Claude Code to behave like different company functions at different moments: founder, engineering manager, designer, QA lead, security officer, release engineer, documentarian, and memory system.

The Instagram reel you shared makes the same point visually: one Claude Code session acting as a messy brain is less useful than several constrained agents with separate jobs. The video shows gstack on GitHub, diagrams of role-specific agents, and the practical advice to start with only two agents: one builder and one reviewer.

The big idea One AI trying to design, build, review, test, document, and ship at the same time will often blur responsibilities. gstack separates those responsibilities into repeatable commands, so each mode has a narrower job and a stronger checklist.

What gstack actually is

gstack is an open-source repository by Garry Tan. The README describes it as his exact Claude Code setup and a "virtual engineering team." The current repository I inspected is version 1.58.5.0, MIT licensed, and has grown beyond the original viral summary: I counted 54 SKILL.md files in the cloned repo.

The viral shorthand is still useful: gstack became popular as "23 specialists and 8 power tools." But the repo is now larger. It contains slash-command skills for planning, design, engineering review, QA, security, release, browser work, documentation, memory, iOS QA, diagrams, PDFs, and cross-agent workflows.

The important thing: these are not magic autonomous employees. They are structured operating procedures written as skills. They tell the model what role to play, when to invoke that mode, what evidence to collect, what to avoid, and how to hand work to the next step.

Not one botIt splits work into modes: CEO, eng manager, designer, reviewer, QA, security, release, docs, memory.
Not just promptsMany skills include preambles, checks, tool rules, browser flows, review gates, and handoff conventions.
Not Claude-only anymoreThe README lists install targets for Claude Code, Codex CLI, OpenCode, Cursor, Factory Droid, Slate, Kiro, Hermes, and GBrain.
Not a replacement for judgmentIt gives structure, but you still approve product direction, security tradeoffs, merge decisions, and deployment risk.

The roles that matter most

You do not need to memorize every command. Understand the workflow: think, plan, build, review, test, ship, document, learn. That is the real architecture.

/office-hoursYC-style product partnerInterrogate the idea before you build. It asks forcing questions and reframes vague product requests into sharper wedges.
/plan-ceo-reviewCEO / founderChallenge scope, market framing, and product ambition. It tries to find the stronger product hidden inside the request.
/plan-eng-reviewEngineering managerTurn product direction into architecture, data flow, state transitions, failure modes, edge cases, and test plans.
/plan-design-reviewSenior designerReview the plan from a design-quality angle and push against generic AI UI, unclear hierarchy, and weak interaction decisions.
/reviewStaff engineerReview code before landing. It looks for production bugs, completeness gaps, and risky assumptions.
/qaQA leadUse a real browser to test the app, find bugs, fix them, and re-verify behavior.
/csoChief security officerRun security review with OWASP and STRIDE-style thinking. The goal is fewer vague warnings and more concrete exploit scenarios.
/shipRelease engineerSync with base, run tests, review diff, commit, push, and open a PR.
/document-releaseTechnical writerUpdate documentation after shipping so README, changelog, and how-to docs do not drift from the code.
/learnMemory managerTrack reusable project lessons, preferences, pitfalls, and patterns across sessions.

Why role-based agents work better than one giant prompt

The usual Claude Code mistake is asking one model to do everything in one run: "build this feature, make it look good, test it, fix bugs, update docs, and deploy." The model may comply, but the quality of each responsibility varies because the prompt is asking for conflicting mental modes.

A designer should be sensitive to visual hierarchy, spacing, empty states, and user emotion. A QA lead should be suspicious, repetitive, and happy to break things. A release engineer should be boring and procedural. A CEO reviewer should ask whether the whole thing is worth building. Those are different modes.

gstack's bet is simple: instead of one overloaded assistant, use specialized passes. Let the CEO agent challenge the idea. Let the engineering manager lock down the architecture. Let the builder implement. Let the reviewer attack the diff. Let QA click the app. Let release ship only after the boring checks pass.

A useful mental model Do not think of gstack as 23 people. Think of it as 23 checklists with personalities. The personality makes the model behave differently; the checklist keeps it from drifting.

How to install it

The official README gives a Claude Code install command. Open Claude Code and run:

git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/.claude/skills/gstack
cd ~/.claude/skills/gstack
./setup

For Codex CLI, the README says the setup script can target different hosts. A practical Codex install path is:

git clone --single-branch --depth 1 https://github.com/garrytan/gstack.git ~/gstack
cd ~/gstack
./setup --host codex

For team mode, gstack can add repo-level configuration so teammates get the same skills automatically. The README shows:

(cd ~/.claude/skills/gstack && ./setup --team) \
  && ~/.claude/skills/gstack/bin/gstack-team-init required \
  && git add .claude/ CLAUDE.md \
  && git commit -m "require gstack for AI-assisted work"

Do not blindly run team mode in a work repo. It changes project files and creates a team convention. Use it only when the team agrees that gstack should be part of the repo workflow.

You do not need 23 agents. Start with two.

The reel's strongest practical point is this: beginners should not copy the whole system on day one. Start with a builder and a reviewer. That single separation already changes the quality of your Claude Code sessions.

Agent 1: Builder

The builder implements the feature. It should stay scoped, read the codebase first, make the smallest useful change, and verify what it changed.

Use builder mode.

Goal: implement [specific feature].
Scope: only touch files needed for this feature.
Do not refactor unrelated code.
Before editing, inspect the existing patterns.
After editing, run the relevant build/test command.
Report what changed and what verification passed.

Agent 2: Reviewer

The reviewer should be adversarial. It should not praise the work first. It should hunt for bugs, missing states, broken assumptions, accessibility issues, security gaps, and missing tests.

Use reviewer mode.

Review the current diff as if it is going to production today.
Lead with findings, ordered by severity.
Focus on bugs, regressions, missing tests, security risk, UX edge cases, and maintainability.
Use file and line references.
If there are no findings, say that clearly and list residual risk.

Once this feels natural, add a third role: QA. Have it open the app, click the flow, and confirm the thing actually works. The jump from "code compiles" to "user flow works" is where many AI-generated features fail.

A practical gstack workflow for solo builders

  1. Start with the pain. Use /office-hours or your own product-question prompt. Explain the actual user problem, not just the feature idea.
  2. Plan before building. Run a CEO-style or engineering-manager-style review. Force the model to expose assumptions before it edits files.
  3. Build in a narrow scope. Use a builder pass. Keep the implementation boring and local.
  4. Review the diff separately. Use /review or a reviewer prompt. Do not let the same run that wrote the code be the only judge of the code.
  5. QA in the browser. Use /qa for real user flows. Browser clicks catch problems a unit test will never see.
  6. Ship with ceremony. Use /ship or your own release checklist. Sync base, run tests, check diff, push, PR.
  7. Update docs and memory. Use /document-release and /learn so the next session has more context than the last one.

Where gstack can go wrong

gstack is powerful, but it is also opinionated. That is the tradeoff. You get Garry Tan's product and engineering taste encoded as workflows. That can be a huge advantage for founder-style product building. It can also be too heavy for small tasks or too YC-flavored for enterprise work with existing RFC processes.

OverheadA typo fix does not need CEO review, design review, QA, release ceremony, and docs. Use the system only when the task deserves it.
False confidenceMultiple agents can still share the same blind spot if they all rely on the same wrong context. Verification matters more than personas.
Workflow mismatchA startup product workflow is not always right for regulated enterprise software, legacy migrations, or teams with strict architecture boards.
SecuritySkills are instructions plus scripts. Read what you install, especially before enabling browser, deploy, or repo-wide team workflows.
My recommendation Install it in a sandbox repo first. Try /office-hours, /plan-eng-review, /review, and /qa. If those improve your work, then consider adding more.

The real lesson

The point is not "use 23 agents because Garry Tan does." The point is that AI coding gets better when you stop treating the model as one magical brain and start treating it as a set of constrained roles.

For a beginner, that means builder plus reviewer. For a serious solo founder, it may mean product review, engineering review, design review, QA, release, and docs. For a team, it may mean standardizing agent behavior so every AI-assisted change goes through the same gates.

gstack is one implementation of that idea. It is not the only one. But it is useful because it shows the shape of where AI coding is going: less "write me code" and more "run a disciplined software process with specialist agents."
