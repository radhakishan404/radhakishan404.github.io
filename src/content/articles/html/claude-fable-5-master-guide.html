What changed with Fable 5?

Fable 5 should not be prompted like a chatbot that answers one small question. It is designed for bigger work: multi-step engineering, long investigations, code review, image understanding, document workflows, and agent orchestration.

The main shift is this: you can give it a real outcome, explain why it matters, set boundaries, and let it work. The prompt becomes less like a question and more like a compact operating brief.

Fable 5 ko normal chatbot ki tarah prompt mat karo. Ye bigger work ke liye bana hai: multi-step engineering, long investigation, code review, image understanding, document workflows, aur agent orchestration.

Main change ye hai: aap outcome batao, reason batao, boundaries set karo, aur model ko kaam karne do. Prompt ek simple question nahi, ek short operating brief ban jata hai.

Core principles

Use effort deliberately

Higher effort gives stronger planning and checking, but can be slower. Use high for serious tasks, lower effort for routine edits.

Higher effort se planning/checking better hoti hai, but slow ho sakta hai. Serious task ke liye high, routine edits ke liye lower effort.

Stop unnecessary cleanup

Fable 5 may improve nearby code or create extra structure. Tell it to do the smallest useful change unless you ask for a refactor.

Fable 5 kabhi nearby cleanup/refactor kar sakta hai. Clear bolo: sirf required change karo, refactor tabhi jab bola ho.

Ground progress in evidence

For long runs, ask it to report only what tool results, tests, files, or logs actually prove.

Long runs me bolo: sirf wahi progress report karo jo tool result, test, file, ya log se prove hoti ho.

Give boundaries

If you only want assessment, say so. If changing files is allowed, say exactly where and how far it can go.

Agar sirf assessment chahiye to clear bolo. Agar file change allowed hai, to scope exactly batao.

Use subagents for independent work

Fable 5 is strong at delegation. Let it split independent research, verification, and implementation checks.

Fable 5 delegation me strong hai. Research, verification, implementation checks ko independent split karne do.

Build memory

For repeated workflows, store lessons in small notes. One lesson per file is easier to reuse than one giant memory dump.

Repeated workflows ke liye small notes me lessons save karo. One lesson per file, giant memory dump se better hota hai.

Copy-ready prompt templates

Use these as starting points. Replace the bracketed parts with your real project details.

Inhe starting point ki tarah use karo. Brackets wale parts apne real project details se replace karo.

1. Long-running implementation prompt
Goal: Implement [specific outcome] in [repo/app].

Context: This matters because [business/user reason]. Current behavior is [current state]. Desired behavior is [target state].

Constraints:
- Change only the files needed for this outcome.
- Do not refactor unrelated code.
- Do not add abstractions for hypothetical future needs.
- If you make progress claims, ground them in actual tool results.

Verification:
- Run [tests/build/lint].
- Inspect the generated output.
- Report exactly what passed, failed, or was skipped.
2. Code review prompt
Review [branch/diff/path] for bugs, regressions, missing tests, security risks, and UX edge cases.

Lead with findings ordered by severity.
Use file and line references.
Do not summarize the change before the findings.
If there are no issues, say that clearly and mention residual risk.
3. Evidence-based progress prompt
Before every status update, audit each claim against evidence from this session.

Only say work is complete if a command, file, test, screenshot, or direct inspection proves it.
If something is not verified, label it as unverified.
If tests fail, include the failing output and the next concrete fix.
4. Hinglish learning prompt
Explain [topic] in simple Hinglish for a developer who knows basics but gets confused by jargon.

Use this structure:
1. One-line meaning
2. Real-world analogy
3. Technical explanation
4. Common mistake
5. Small example
6. One practice task

Migration checklist

  • Raise task difficulty. Test Fable 5 on problems that were too hard for prior models.
  • Review old prompts. Remove overly strict instructions that were only needed for weaker models.
  • Add timeout and progress UX for long-running workflows.
  • Make verification explicit, especially for code, documents, and multi-agent runs.
  • Do not ask the model to reveal private reasoning. Ask for a useful summary, decision, or evidence instead.
  • Use a user-facing message tool if your product needs to show mid-run deliverables without ending the run.
  • Task difficulty increase karo. Fable 5 ko un problems par test karo jo earlier models ke liye hard the.
  • Old prompts review karo. Weaker models ke liye jo extra strict rules likhe the, unhe remove/shorten karo.
  • Long-running workflows ke liye timeout aur progress UX add karo.
  • Code, docs, aur multi-agent runs me verification clear rakho.
  • Model se private reasoning reveal karne ko mat bolo. Useful summary, decision, ya evidence mango.
  • Agar product ko mid-run deliverables show karne hain, user-facing message tool design karo.
Bottom line: Fable 5 rewards clear outcomes, useful context, explicit boundaries, and evidence-based reporting.
